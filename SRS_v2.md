## 1. Introduction

### 1.1 Purpose

This SRS defines the complete requirements for **ClinIQ v2**, extending v1 with an AI-powered Health Assistant feature. The assistant enables patients to receive plain-language summaries of their medical history and ask contextual health questions, answered by Google Gemini with grounding in the patient's own clinical data.

### 1.2 Scope *(updated)*

All v1.2 scope is retained. v2 adds:

- AI-powered patient health summary generation (Gemini LLM)
- Conversational AI chat grounded in the patient's own appointments, diagnoses, prescriptions, lab results, and clinical records
- Suggested follow-up questions generated by the AI
- Chat history stored in browser session (not persisted to DB — stateless on the server)
- Patient-portal-only feature; not exposed to admin role

**Out of scope for v2:** AI-generated prescriptions or diagnoses, admin AI analytics, persistent chat history in DB, voice input, PDF export of summaries.

### 1.3 Definitions, Acronyms, and Abbreviations *(extended)*

All v1.2 terms retained. Additions:

| Term | Meaning |
|---|---|
| LLM | Large Language Model |
| Gemini | Google's multimodal LLM (gemini-2.0-flash via Generative Language API) |
| RAG | Retrieval-Augmented Generation — grounding LLM responses in structured data |
| Context window | The patient's full medical data serialized and injected into the prompt |
| Suggested questions | Follow-up question chips generated by the AI after each response |
| Summary | One-shot AI-generated plain-language overview of the patient's health history |

### 1.4 References

All v1.2 references retained. Additions:
- Google Generative AI API documentation (gemini-2.0-flash)
- `google-generativeai` Python SDK

## 2. Overall Description

### 2.1 Product Perspective *(updated)*

v2 system flow adds an AI path:

```
Patient → React Frontend → FastAPI → [PostgreSQL patient data] → Gemini API → FastAPI → React Frontend
```

The backend assembles the patient's full medical context from PostgreSQL, prepends it as a system prompt, and sends the patient's question to Gemini. The response is returned to the frontend. No patient data is stored by Gemini beyond the API call lifetime.

### 2.2 Product Functions *(updated)*

All v1.2 functions retained. Additions:

- **AI Health Summary:** Generate a structured, plain-language summary of a patient's medical history on demand
- **AI Chat:** Answer free-text patient health questions grounded in their own clinical data
- **Suggested Questions:** Surface 3 contextual follow-up questions after each AI response to guide the patient

### 2.3 User Characteristics *(updated)*

v1.2 user table retained. AI feature is available only to the `patient` role:

| Role | AI Feature Access |
|---|---|
| `admin` | None — AI feature not shown in admin portal |
| `patient` | Full access: health summary + chat, scoped to own data |

### 2.4 Constraints *(updated)*

All v1.2 constraints retained. Additions:

- The AI feature requires a valid `GEMINI_API_KEY` set in `.env`
- Patient data sent to Gemini is limited to the authenticated patient's own records (enforced server-side)
- No patient data is logged or persisted by the AI route beyond the HTTP request/response cycle
- Gemini responses must include a disclaimer that they are informational only and not medical advice

### 2.5 Assumptions and Dependencies

All v1.2 assumptions retained. Additions:

- A valid Google Gemini API key is provided and configured in backend `.env`
- The `google-generativeai` Python package is installable in the backend venv
- Internet access is available from the backend server to reach `generativelanguage.googleapis.com`

## 6. Backend Specifications

### 6.1 REST API Endpoints *(updated)*

All v1.2 endpoints retained. New endpoints:

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| POST | /ai/summary | Bearer, role=patient | Generate a plain-language health summary for the authenticated patient |
| POST | /ai/chat | Bearer, role=patient | Answer a patient question grounded in their medical data |

**`POST /ai/summary`**
- Request body: `{}` (no body required — patient identity from JWT)
- Response: `{ "summary": "<markdown string>", "disclaimer": "<string>" }`
- Backend flow: fetch patient data from DB → build system prompt → call Gemini → return response

**`POST /ai/chat`**
- Request body: `{ "message": "<string>", "history": [{ "role": "user"|"model", "content": "<string>" }] }`
- Response: `{ "reply": "<markdown string>", "suggested_questions": ["<q1>", "<q2>", "<q3>"], "disclaimer": "<string>" }`
- Backend flow: fetch patient data → build system prompt with data + history → call Gemini → parse response

**System prompt structure (both endpoints):**
```
You are a helpful medical AI assistant for ClinIQ.
You are speaking with a patient. Their medical data is below.
Answer only based on the provided data. Be clear, compassionate, and concise.
Always end with: "This is informational only and not medical advice."

--- PATIENT MEDICAL CONTEXT ---
[serialized patient data: appointments, diagnoses, prescriptions, labs, clinical records]
--- END CONTEXT ---
```

### 7.3 AI Health Assistant *(new)*

The AI assistant follows a retrieval-augmented generation (RAG) pattern without a vector store:

1. **Retrieval:** Backend fetches structured patient data from PostgreSQL (appointments, diagnoses, prescriptions, lab results, clinical records)
2. **Serialization:** Data is serialized into a human-readable text block injected as the system context
3. **Generation:** Gemini generates a response constrained to the provided context
4. **Safety:** Patient data is scoped by JWT `patient_id`; no cross-patient data leakage possible
